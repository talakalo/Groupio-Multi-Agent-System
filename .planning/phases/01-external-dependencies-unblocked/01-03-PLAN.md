    ### Risks and mitigations

    | Risk | Mitigation |
    |------|------------|
    | Asyncpg "prepared statement already exists" errors after switchover | Plan 01-01's `statement_cache_size=0` is the documented fix. If errors still appear, the URL is not on port 6543 (re-check) or a stale connection is cached (restart the API). |

    | `SET LOCAL` per-request variables (used in Phase 2 RLS work) | Compatible with transaction mode IF issued at the start of each transaction. Phase 2 plans must verify at design time. |
    | Inactivity pause re-enabled by accident | Pro tier never pauses; the dashboard "Pause" setting must read **Never**. Re-check after every billing change. |

    ### Rollback

    If the production app fails to acquire DB connections after the swap:

    1. Revert `DATABASE_URL` in the secret store to the previous direct (port `5432`,
       `db.<ref>.supabase.co`) connection string.
    2. Restart the API (`docker compose -f docker/docker-compose.yml restart backend`).
    3. The asyncpg pool will reconnect; `statement_cache_size=0` is harmless against the
       direct host (slight perf cost only).
    4. Open a Supabase support ticket from the dashboard with the failing connection log lines.
